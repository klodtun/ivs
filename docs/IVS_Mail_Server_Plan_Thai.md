# แผนการพัฒนา Mail Server สำหรับ iVS

เอกสารฉบับนี้เป็นแผนการพัฒนาระบบจดหมายอิเล็กทรอนิกส์ (Mail Server) ให้เป็นโมดูลหนึ่งของ
iVS (Internal Vibe Server) โดยยึดหลักการเดิมของผลิตภัณฑ์ คือ ติดตั้งบนเครื่องเดียว
ใช้งานในเครือข่ายภายในเป็นหลัก ไม่ต้องมีผู้ดูแลระบบเฉพาะทาง และทุกอย่างที่แตะข้อมูลส่วนบุคคล
ต้องมีทะเบียน ROPA บันทึกตรวจสอบ และนโยบายเก็บรักษากำกับเสมอ

> แหล่งอ้างอิง: แผนฉบับนี้จัดทำจากโครงสร้างจริงของโค้ด iVS (รุ่น 1.9.2 ในฝั่งหลังบ้าน)
> ร่วมกับข้อเสนอเบื้องต้นเรื่อง "Mail Server by iVS" ที่เลือก Stalwart เป็นแกนหลักและ
> Docker Mailserver เป็นตัวเลือกสำรอง ซึ่งผู้มีอำนาจตัดสินใจได้ยืนยันแนวทางแล้ว
> ข้อสรุปจากข้อเสนอนั้นถูกรวมไว้ในหัวข้อ 4, 9 และ 12 โดยตรง

## 2. บริบทของ iVS ที่แผนนี้ต้องเคารพ

สิ่งที่ตรวจพบในโค้ดและมีผลโดยตรงต่อการออกแบบ

1. **ระบบยังไม่มีความสามารถส่งจดหมายเลย** ไม่มีการตั้งค่า SMTP ในฝั่งหลังบ้าน ไม่มีเทมเพลตจดหมาย
   คำว่า SMTP ปรากฏเพียงในฐานะ "การพึ่งพาภายนอก" ของแอปที่ดีพลอย (`DependencyKind.EXTERNAL`)
   นั่นหมายความว่าแอปของผู้ใช้ที่ต้องส่งจดหมาย ต้องวิ่งออกนอกองค์กรเสมอในปัจจุบัน
2. **โครงสร้างบริการแบบคอนเทนเนอร์เสริมมีแบบอย่างแล้ว** Caddy, CoreDNS และ Gitea เป็นบริการ
   ที่ iVS ควบคุมผ่าน API ของตัวมันเอง (dns_service ยิง REST API ของ Caddy ที่พอร์ต 2019)
   Mail Server ควรเดินตามแบบนี้ ไม่ใช่ติดตั้งเป็น "แอป" ที่ผู้ใช้ลากวาง
3. **คลังกุญแจ (Vault) และการฉีดตัวแปรแวดล้อม** มีอยู่แล้ว (vault_service, build_env_dict)
   รหัสผ่านบัญชีจดหมายต่อแอป จึงควรเก็บและส่งให้แอปด้วยกลไกนี้ ไม่สร้างกลไกใหม่
4. **เมนูมาจากหลังบ้าน** แถบเมนูอ่าน `visible_menus()` จาก variants.py การเพิ่มหน้าใหม่ต้อง
   ลงทะเบียนในพจนานุกรม `MODULES` ก่อน
5. **ข้อห้ามด้านปฏิบัติการ** ตาม OPERATIONS.md ได้แก่ ธง `data/EVENT-LIVE` ที่ห้ามรีสตาร์ตทุกอย่าง,
   ตัวการ์ดที่ห้ามลบคอนเทนเนอร์ `ivs-*` และห้ามลบ volume, และกฎว่าแถว ROPA ไม่มีวันถูกลบ
   โมดูลจดหมายต้องทำงานภายใต้กฎเหล่านี้ทั้งหมด
6. **ชื่อโดเมนภายใน** ใช้ `*.vibe.local` ผ่าน CoreDNS ซึ่งปัจจุบันใช้ปลั๊กอิน `hosts`
   ที่ตอบได้เฉพาะระเบียน A ไม่ตอบระเบียน MX จึงต้องปรับ Corefile เมื่อถึงระยะที่ 1
7. **ทรัพยากรขั้นต่ำ 4 GB RAM** ตัดตัวเลือกอย่าง Mailcow (ต้องการราว 6 GB) ออกไปโดยปริยาย
8. **สภาพเครื่องจริง ณ วันจัดทำ** Caddy ไม่ได้รัน ทำให้ทุก URL ที่ระบบแจกเป็น HTTP ล้วน
   เว็บเมลและหน้าผู้ดูแลจดหมายต้องการ HTTPS เงื่อนไขก่อนเริ่มระยะที่ 1 คือ Caddy ต้องทำงานปกติ

## 3. ขอบเขตและสิ่งที่ไม่ทำ

### 3.1 อยู่ในขอบเขต

- จดหมายแจ้งเตือนจากตัว iVS เอง (รหัสผ่านชั่วคราว, ผลการส่งออกบันทึกตรวจสอบ, คำขอลบข้อมูล,
  แอปล้ม, อุโมงค์เชื่อมต่อใกล้หมดอายุ, ใบอนุญาตใกล้หมดอายุ)
- บริการ SMTP สำหรับแอปที่ดีพลอยบนกล่อง พร้อมบัญชีและรหัสผ่านต่อแอป
- กล่องจดหมายของผู้ใช้ภายในองค์กร (IMAP และเว็บเมล) ภายใต้โดเมนภายในและโดเมนจริง
- การรับส่งกับอินเทอร์เน็ตแบบมีมาตรฐานความน่าเชื่อถือครบ (SPF, DKIM, DMARC, TLS)
- การกำกับดูแลตาม PDPA, พ.ร.บ.คอมพิวเตอร์ (ข้อมูลจราจร), การสำรองข้อมูล และบันทึกตรวจสอบ

### 3.2 นอกขอบเขต (อย่างน้อยในรอบนี้)

- ปฏิทิน รายชื่อผู้ติดต่อแบบ CardDAV/CalDAV และการประชุม
- การย้ายกล่องจดหมายจำนวนมากจากระบบเดิม (ให้เป็นบริการติดตั้งแยก)
- การเก็บถาวรเพื่อการฟ้องร้อง (legal hold) ระดับองค์กรใหญ่
- การรับส่งหลายเครื่อง (ตกไปที่รุ่น Enterprise)

## 4. ทางเลือกซอฟต์แวร์และข้อเสนอ

| ตัวเลือก | ข้อดี | ข้อด้อย | เหมาะกับ iVS หรือไม่ |
| --- | --- | --- | --- |
| **Stalwart Mail Server** | ไบนารีเดียว, SMTP + IMAP + JMAP + ManageSieve, DKIM/SPF/DMARC/ARC และตัวกรองสแปมในตัว, ตั้งค่าผ่าน REST API, ใช้หน่วยความจำต่ำ, รองรับ SQLite เป็นที่เก็บข้อมูล, มีหน้าผู้ดูแลเว็บ | โครงการค่อนข้างใหม่, ชุมชนเล็กกว่า Postfix, อาจต้องติดตั้งเว็บเมลเพิ่มถ้ารุ่นที่ใช้ยังไม่มีในตัว | **แนะนำ** ตรงปรัชญา "ชิ้นเดียว ควบคุมผ่าน API" เหมือนที่ iVS ทำกับ Caddy |
| Postfix + Dovecot + Rspamd + OpenDKIM | มาตรฐานอุตสาหกรรม เอกสารมาก พิสูจน์แล้วหลายสิบปี | ประกอบจาก 4 ถึง 6 ส่วน ตั้งค่าหลายไฟล์ ไม่มี API กลาง ดูแลยากสำหรับผู้ใช้ที่ "ไม่ต้องมี DevOps" | ไม่แนะนำเป็นแกน แต่ใช้เป็นแผนสำรองได้ |
| Mailu | แบ่งเป็นส่วนย่อยชัดเจน มีหน้าผู้ดูแลและเว็บเมลมาด้วย | หลายคอนเทนเนอร์ (Postfix, Dovecot, Rspamd, หน้าผู้ดูแล, เว็บเมล) ต้องดูแลร่วมกัน | พอใช้ได้ แต่ซ้อนทับหน้าที่ของ iVS และ Caddy |
| Mailcow (dockerized) | ครบวงจร มีเว็บเมลและหน้าผู้ดูแลสำเร็จรูป | ใช้ RAM มาก เอกสารทางการระบุขั้นต่ำ 6 GB พร้อม Swap 1 GB, มีคอนเทนเนอร์นับสิบตัว, มี Nginx ของตัวเองซ้อนกับ Caddy และ **เอกสารทางการระบุว่าไม่แนะนำให้ติดตั้งบน Synology/QNAP NAS โดยตรง** | ไม่ผ่านเกณฑ์ทรัพยากรและกลุ่มเครื่องเป้าหมายของ iVS |
| Maddy | เบามาก ไบนารีเดียว | ไม่มีหน้าผู้ดูแล, ไม่มีตัวกรองสแปมในตัว, ฟีเจอร์น้อยกว่า | เหมาะเฉพาะกรณีส่งออกอย่างเดียว |
| Docker Mailserver | ประกอบ Postfix/Dovecot/Rspamd ไว้ให้แล้วในคอนเทนเนอร์เดียว เบา เหมาะเป็นบริการจดหมายหลังบ้าน | ตั้งค่าผ่านตัวแปรแวดล้อมและสคริปต์ ไม่มี API กลาง ไม่มีเว็บเมล ต้องพัฒนาหน้าจอจัดการเองทั้งหมด | **ตัวเลือกสำรองอันดับ 1** สำหรับระบบที่ต้องการความเรียบง่าย |

**ข้อตัดสินใจ (ยืนยันแล้ว):** ใช้ Stalwart Mail Server เป็นเครื่องยนต์จดหมาย (Mail Engine)
และให้ iVS เป็นชั้นบริหารจัดการ (Management Layer) โดยมี Docker Mailserver เป็นตัวเลือกสำรอง
สำหรับระบบที่ต้องการความเรียบง่าย

หลักการที่ต้องยึดตลอดการพัฒนา

1. **ไม่ Fork Stalwart** ไม่นำซอร์สโค้ดของ Stalwart มาแก้แล้วปล่อยเป็นของตัวเอง ใช้ภาพคอนเทนเนอร์
   ทางการที่ตรึงรุ่นไว้ และสื่อสารกับมันผ่าน REST API และ JMAP เท่านั้น เหตุผลคือ ทีมเล็กตามอัปเดต
   ด้านความปลอดภัยของซอฟต์แวร์จดหมายไม่ทัน และการ fork ทำให้ขายเชิงพาณิชย์ยากขึ้นเพราะต้องรับผิดชอบ
   โค้ดทั้งก้อน
2. **แยกเว็บเมลของผู้ใช้ออกจากหน้าผู้ดูแลของ Stalwart** หน้าผู้ดูแล Stalwart ให้ใช้เฉพาะงานซ่อมบำรุง
   เชิงลึกและซ่อนไว้หลัง app_gate ส่วนงานประจำวัน (โดเมน, กล่องจดหมาย, โควตา) ทำผ่านหน้าจอของ iVS
   และเว็บเมลสำหรับผู้ใช้ทั่วไปเป็นคอนเทนเนอร์แยกชื่อ `ivs-webmail` ถ้ารุ่น Stalwart ที่นำมาใช้
   มีเว็บเมลในตัวและใช้งานภาษาไทยได้ดี ให้ใช้ของมัน มิฉะนั้นใช้ Roundcube (ภาษาไทยครบ ผู้ใช้ไทยคุ้นเคย)
   ทั้งสองกรณีอยู่หลัง Caddy เสมอ
3. **ชื่อผลิตภัณฑ์** ใช้ชื่อ "Mail Server by iVS" ในการสื่อสารภายนอก และใช้คีย์โมดูล `mail` ในโค้ด

ให้ทดสอบ Stalwart เทียบกับตัวเลือกสำรอง (Docker Mailserver) ในสัปดาห์แรกของระยะที่ 1 ด้วยเกณฑ์ตายตัว
(ติดตั้งบน Synology ได้, RAM ที่ใช้จริง, สร้างบัญชีผ่าน API ได้, รับส่งภายใน LAN ได้) เพื่อยืนยัน
ด้วยของจริงครั้งเดียว ไม่เปลี่ยนกลางทาง

### 4.1 รูปแบบการติดตั้ง: บริการที่ iVS ดูแล ไม่ใช่ "แอป" ที่ผู้ใช้ลากวาง

ข้อเสนอเบื้องต้นเสนอให้ทำ Stalwart เป็น "แม่แบบแอป" (Application Template) ที่ดีพลอยผ่านกลไกแอป
ปกติของ iVS แผนฉบับนี้**เลือกไม่ทำแบบนั้น** และกำหนดให้ `ivs-mail` เป็นบริการระดับแพลตฟอร์ม
แบบเดียวกับ Caddy, CoreDNS และ Gitea ด้วยเหตุผลที่มาจากพฤติกรรมจริงของ iVS

| ประเด็น | ถ้าเป็น "แอป" ที่ดีพลอย | ถ้าเป็นบริการที่ iVS ดูแล (ที่เลือก) |
| --- | --- | --- |
| การดีพลอยซ้ำ | OPERATIONS.md ระบุว่าการดีพลอยซ้ำ **ลบข้อมูลของแอปทิ้ง** กล่องจดหมายทั้งองค์กรจึงหายได้ด้วยปุ่มเดียว | volume `mail_data` อยู่นอกวงจรดีพลอยของแอป ไม่มีปุ่มใดบนหน้าจอลบมันได้ |
| พอร์ต | แอปได้พอร์ตจากช่วง 10000–10999 ไม่ใช่ 25/465/587/993 | ผูกพอร์ตมาตรฐานของจดหมายได้โดยตรง |
| การควบคุม | iVS มองเป็นกล่องดำ สร้างบัญชี/โดเมนจากหน้าจอ iVS ไม่ได้ | `mail_server_service` คุมผ่าน REST API เหมือน dns_service คุม Caddy |
| การผูกกับผู้ใช้ iVS | ต้องเขียนกาวเชื่อมภายนอก | ซิงก์บัญชี ปิดบัญชี และฉีด SMTP ให้แอปอื่นได้จากในแกน |
| ตัวการ์ดคำสั่ง | ไม่ครอบคลุม | ชื่อ `ivs-mail` ถูกกฎ `ivs-*` คุ้มครองอยู่แล้ว |

สิ่งที่ยังนำจากข้อเสนอเดิมมาใช้ได้เต็มที่คือ **บทบาท**: iVS เป็นแพลตฟอร์มดีพลอยและบริหาร
Stalwart เป็นเครื่องยนต์ และข้อมูลถาวรทั้งหมดอยู่บนดิสก์หรือ NAS ของกล่องนั้นเอง

```
      │  - SMTP รับ/ส่ง, คิว, DKIM, SPF/DMARC, ตัวกรองสแปม  │
      │  - IMAP/JMAP สำหรับผู้ใช้                           │
      │  - REST API ผู้ดูแล (ภายใน ivs-internal เท่านั้น)   │
      └───────────▲──────────────────────────▲──────────────┘
                  │ REST API (บัญชี/โดเมน/DKIM) │ SMTP 587 + รหัสต่อแอป
      ┌───────────┴───────────┐     ┌──────────┴──────────────┐
      │ ivs-backend           │     │ แอปที่ดีพลอย (ivs-apps) │
      │ mail_service.py       │     │ ได้ SMTP_* จากคลังกุญแจ │
      │ mail_server_service.py│     └─────────────────────────┘
      │ routers/mail.py       │
      └───────────▲───────────┘
                  │
      ┌───────────┴───────────┐     ┌─────────────────────────┐
      │ ivs-frontend          │     │ ivs-caddy               │
      │ /dashboard/mail       │◄────┤ mail.vibe.local (เว็บเมล│
      └───────────────────────┘     │ + หน้าผู้ดูแล, HTTPS)   │
                                    └─────────────────────────┘
      ┌───────────────────────┐
      │ ivs-coredns           │  ระเบียน A และ MX ของ vibe.local
      └───────────────────────┘
```

### 5.1 ส่วนประกอบใหม่ในฝั่งหลังบ้าน

| ไฟล์ | หน้าที่ |
| --- | --- |
| `app/services/mail_service.py` | ส่งจดหมายของ iVS เอง: เทมเพลต Jinja2 สองภาษา, ตารางคิว `mail_outbox`, การลองส่งซ้ำแบบถอยหลัง, บันทึกผลลง audit |
| `app/services/mail_server_service.py` | ควบคุม Stalwart ผ่าน REST API: สร้าง/ปิดบัญชี, โดเมน, สร้างคู่กุญแจ DKIM, อ่านสถานะคิว, อ่านสถิติ (แบบอย่างคือ dns_service ที่คุม Caddy) |
| `app/routers/mail.py` | เส้นทาง `/api/mail/*` ทุกเส้นมี `require_role` ชัดเจน |
| `app/models.py` (เพิ่มตาราง) | `MailDomain`, `MailAccount`, `MailOutbox`, `MailDelivery` (บันทึกการส่ง ไม่เก็บเนื้อหา) |
| `app/variants.py` | เพิ่ม `MODULES["mail"] = {"menu": "/dashboard/mail", "th": "จดหมาย", ...}` และใส่ในรุ่นย่อยที่เหมาะสม |
| `docker-compose.mail.yml` | ไฟล์ซ้อน (overlay) เพิ่มบริการ `ivs-mail` และ `ivs-webmail` ให้เปิดใช้เฉพาะกล่องที่เปิดโมดูล |

### 5.2 ส่วนประกอบใหม่ในฝั่งหน้าจอ

- หน้า `/dashboard/mail` แบ่งเป็นแถบ: ภาพรวมและคิว, โดเมน, บัญชี, การเชื่อมต่อของแอป, การตั้งค่ารีเลย์
- แถบ "จดหมาย" ในหน้าตั้งค่า สำหรับระยะที่ 0 (ตั้งค่ารีเลย์ภายนอกและผู้รับการแจ้งเตือน)
- ส่วนขยายในการ์ดแอป: ปุ่ม "ให้แอปนี้ส่งจดหมายได้" ซึ่งสร้างบัญชี SMTP ต่อแอปและฉีดตัวแปรแวดล้อมให้

### 5.3 พอร์ตและเครือข่าย

| พอร์ต | ใช้ทำอะไร | เปิดเมื่อใด |
| --- | --- | --- |
| 25/tcp | รับจดหมายจากเซิร์ฟเวอร์อื่น | ระยะที่ 2 เท่านั้น ภายใน LAN ใช้สำหรับระยะที่ 1 ได้ |
| 465/tcp, 587/tcp | ผู้ใช้และแอปส่งจดหมายผ่านการยืนยันตัว | ระยะที่ 1 |
| 143/tcp, 993/tcp | IMAP (ใช้ 993 เป็นหลัก) | ระยะที่ 1 |
| 4190/tcp | ManageSieve (กฎกรองจดหมายฝั่งผู้ใช้) | เลือกได้ |
| 8080 (ภายใน) | REST API และ JMAP ของ Stalwart ให้ Caddy และ backend เท่านั้น ไม่เผยพอร์ตออกจากเครื่อง | ระยะที่ 1 |

หลัก: พอร์ตผู้ดูแลไม่เปิดสู่ภายนอกเครื่อง ทุกอย่างที่เป็น HTTP ต้องผ่าน Caddy

## 6. แผนตามระยะ

### ระยะที่ 0 — iVS ส่งจดหมายแจ้งเตือนได้ (ผ่านตัวรีเลย์ภายนอก)

เป้าหมาย: ได้คุณค่าเร็วที่สุดโดยยังไม่ต้องมีเซิร์ฟเวอร์จดหมายของตัวเอง และวางโครง
mail_service ที่ระยะถัดไปจะใช้ต่อโดยไม่ต้องเขียนใหม่

งาน
1. สร้าง `mail_service.py` พร้อมตารางคิว `mail_outbox` (ผู้รับ, หัวเรื่อง, ชื่อเทมเพลต, ข้อมูลเทมเพลต,
   สถานะ, จำนวนครั้งที่ลอง, ข้อผิดพลาดล่าสุด) และงานพื้นหลังที่ส่งทุก 30 วินาที
   ลองซ้ำแบบถอยหลัง (1, 5, 30 นาที แล้วทิ้งพร้อมบันทึก)
2. เทมเพลต Jinja2 ไทย/อังกฤษ ตามภาษาที่ผู้ใช้เลือกไว้ อย่างน้อย: รหัสผ่านชั่วคราว,
   ส่งออกบันทึกตรวจสอบสำเร็จ (พร้อมค่า SHA-256), คำขอลบข้อมูลดำเนินการแล้ว, แอปหยุดทำงานผิดปกติ,
   อุโมงค์เชื่อมต่อใกล้หมดอายุ, ใบอนุญาตใกล้หมดอายุ
3. การตั้งค่ารีเลย์เก็บใน `SystemConfig` (โฮสต์, พอร์ต, ชนิดการเข้ารหัส, ชื่อผู้ส่ง)
   และรหัสผ่านเก็บในคลังกุญแจ (namespace `ivs/mail`, ไม่อนุญาตเปิดดู) รองรับ Gmail,
   Microsoft 365, และผู้ให้บริการ SMTP ทั่วไป
4. ปุ่ม "ส่งจดหมายทดสอบ" ในหน้าตั้งค่า พร้อมแสดงผลลัพธ์จริงจากเซิร์ฟเวอร์ปลายทาง
5. ทุกการส่งลง `AuditLog` (action `mail.sent` / `mail.failed`) โดยบันทึกผู้รับและหัวเรื่อง
   ไม่บันทึกเนื้อหา
6. เพิ่มแถว ROPA ของกิจกรรม "การแจ้งเตือนทางจดหมาย" (ฐานทางกฎหมาย: ประโยชน์อันชอบธรรม /
   การปฏิบัติตามสัญญา ให้ผู้ควบคุมข้อมูลยืนยัน)

เกณฑ์รับงาน
- ส่งจดหมายทดสอบถึง Gmail และ Microsoft 365 สำเร็จ และผลขัดข้องแสดงข้อความจากเซิร์ฟเวอร์จริง
- ปิดอินเทอร์เน็ตแล้วจดหมายค้างในคิว เมื่อกลับมาส่งสำเร็จเองโดยไม่ซ้ำ
- ไม่มีรหัสผ่านปรากฏในบันทึกใด ๆ

ประมาณการ: 2 สัปดาห์

### ระยะที่ 1 — เซิร์ฟเวอร์จดหมายภายในเครือข่าย (`mail.vibe.local`)

เป้าหมาย: องค์กรที่ใช้ iVS ในเครือข่ายปิด (โรงพยาบาล, โรงงาน, งานอีเวนต์) มีจดหมายภายในได้
และแอปทุกตัวบนกล่องส่งจดหมายผ่าน `ivs-mail` แทนการวิ่งออกนอกองค์กร

งาน
1. `docker-compose.mail.yml`: บริการ `ivs-mail` (Stalwart, volume `mail_data`, จำกัดหน่วยความจำ 1 GB)
   และ `ivs-webmail` (ถ้าจำเป็น) บนเครือข่าย `ivs-internal` และ `ivs-apps`
2. `mail_server_service.py`: ตั้งค่า Stalwart ครั้งแรกอัตโนมัติ (สร้างผู้ดูแล เก็บรหัสในคลังกุญแจ,
   สร้างโดเมน `vibe.local`, ปิดการรีเลย์แบบเปิดอย่างเด็ดขาด, บังคับยืนยันตัวทุกการส่ง, จำกัดอัตราส่ง)
3. **ซิงก์บัญชี**: ผู้ใช้ iVS ที่มีสถานะใช้งาน หนึ่งคนได้หนึ่งกล่องจดหมาย `<username>@vibe.local`
   รหัสผ่านตั้งแยกจากรหัส iVS (เพื่อไม่ให้รหัสระบบรั่วผ่านไคลเอนต์จดหมาย) และต้องผ่าน
   `password_policy` เดียวกับระบบ ปิดบัญชี iVS แล้วกล่องจดหมายถูกปิดตาม แต่ไม่ลบจนครบนโยบายเก็บรักษา
4. **บัญชีต่อแอป**: `app-<slug>@vibe.local` สร้างเมื่อผู้ดูแลกด "ให้แอปนี้ส่งจดหมายได้"
   รหัสเก็บในคลังกุญแจ namespace ของแอป และฉีดเป็น `SMTP_HOST=ivs-mail`, `SMTP_PORT=587`,
   `SMTP_USER`, `SMTP_PASS`, `SMTP_FROM` ตอนดีพลอย พร้อมบันทึกเส้นพึ่งพาใน `app_dependencies`
   (kind `http_api`/ภายใน, origin `declared`) เพื่อให้แผนที่ระบบเห็นเส้นนี้
5. DNS ภายใน: ปรับ `coredns/Corefile` ให้โซน `vibe.local` ตอบระเบียน MX ได้ (ย้ายจากปลั๊กอิน
   `hosts` ไปปลั๊กอิน `file` หรือเพิ่มปลั๊กอิน `template` สำหรับ MX โดยคง `hosts` ไว้สำหรับ A)
   และให้ `dns_service` เขียนระเบียน `mail.vibe.local` เหมือนแอปทั่วไป
6. Caddy: เส้นทาง `mail.vibe.local` ไปเว็บเมล และ `mail.vibe.local/admin` ไปหน้าผู้ดูแล Stalwart
   (จำกัดด้วยบทบาท ADMIN ผ่าน app_gate ของ iVS)
7. หน้า `/dashboard/mail`: ภาพรวมคิว, บัญชี, การเชื่อมต่อของแอป, ปุ่มส่งทดสอบ
8. เปลี่ยนตัวรีเลย์ของระยะที่ 0 ให้ชี้มาที่ `ivs-mail` โดยอัตโนมัติเมื่อโมดูลเปิด
9. `scripts/backup.sh`: เพิ่มการสำรอง volume `mail_data` และการตั้งค่า Stalwart
10. ตัวการ์ด `.claude/hooks/ivs-guard.sh` ครอบคลุม `ivs-mail` อยู่แล้วด้วยกฎ `ivs-*`
    ให้เพิ่มการตรวจธง `EVENT-LIVE` ก่อนทุกคำสั่งรีสตาร์ตโมดูลจดหมายจากหน้าจอด้วย

ข้อจำกัดที่ต้องบอกผู้ใช้ตรง ๆ
- ใบรับรอง TLS ของ `mail.vibe.local` มาจาก CA ภายในของ Caddy หรือ Stalwart ไคลเอนต์จดหมายบนมือถือ
  จะเตือนจนกว่าจะติดตั้ง CA ลงเครื่อง เว็บเมลผ่าน Caddy มีข้อจำกัดเดียวกันตามที่ OPERATIONS.md ระบุ
- เครื่องต้องมี IP คงที่หรือการจอง DHCP มิฉะนั้นระเบียน MX จะชี้ผิดเงียบ ๆ เช่นเดียวกับระเบียน A

เกณฑ์รับงาน
- ผู้ใช้สองคนรับส่งจดหมายกันได้ผ่านเว็บเมลและผ่าน IMAP บนโทรศัพท์ที่ติดตั้ง CA แล้ว
- แอปทดสอบที่ดีพลอยผ่าน iVS ส่งจดหมาย OTP ถึงผู้ใช้ภายในได้ โดยไม่มีการเชื่อมต่อออกอินเทอร์เน็ต
- พยายามส่งโดยไม่ยืนยันตัวหรือจากเครือข่ายอื่นต้องถูกปฏิเสธ (ทดสอบด้วย swaks)
- ปิดบัญชีผู้ใช้ใน iVS แล้วเข้าสู่ระบบ IMAP ไม่ได้ภายใน 1 นาที

ประมาณการ: 4 สัปดาห์ (รวม 1 สัปดาห์ทดสอบเปรียบเทียบซอฟต์แวร์)

### ระยะที่ 2 — รับส่งกับอินเทอร์เน็ตด้วยโดเมนจริง

เป้าหมาย: องค์กรที่มีโดเมนของตัวเอง เช่น `example.co.th` ใช้กล่อง iVS เป็นเซิร์ฟเวอร์จดหมายจริง

เงื่อนไขก่อนเริ่ม (ตรวจอัตโนมัติในหน้าจอก่อนให้กดเปิด)
1. มี IP สาธารณะคงที่ และผู้ให้บริการอินเทอร์เน็ตตั้งระเบียน PTR (reverse DNS) ให้ชี้กลับมาที่
   ชื่อโฮสต์จดหมายได้ (ผู้ให้บริการสำหรับบ้านพักอาศัยในไทยส่วนใหญ่ไม่ให้บริการนี้)
2. พอร์ต 25 ขาออกไม่ถูกบล็อก ถ้าถูกบล็อก ให้ใช้ **โหมดลูกผสม**: รับเข้าโดยตรง แต่ส่งออกผ่าน
   ตัวรีเลย์ (smarthost) ของผู้ให้บริการ เช่น Amazon SES, SMTP2GO, Postmark ซึ่งระยะที่ 0 รองรับไว้แล้ว
3. ควบคุม DNS ของโดเมนได้ (เพิ่มระเบียน MX, A, TXT, CNAME)

งาน
1. หน้าจอ "เพิ่มโดเมน" ที่สร้างรายการระเบียน DNS ให้คัดลอกครบชุด: MX, A/AAAA ของ `mail.`,
   SPF (`v=spf1 mx -all` หรือรวมรีเลย์), DKIM (คู่กุญแจที่ Stalwart สร้าง, หมุนกุญแจได้),
   DMARC (เริ่มที่ `p=none` พร้อมที่อยู่รับรายงาน แล้วค่อยขยับไป `quarantine`/`reject`),
   MTA-STS และ TLS-RPT (เลือกได้), autodiscover/autoconfig สำหรับไคลเอนต์
2. ตัวตรวจระเบียน DNS จากในหน้าจอ (ใช้ `dnspython`) แสดงเขียว/แดงต่อระเบียน และคอยตรวจซ้ำ
3. ใบรับรองจริงจาก Let's Encrypt: ให้ Stalwart ขอด้วย ACME เอง (HTTP-01 ผ่าน Caddy หรือ
   DNS-01 ถ้าผู้ให้บริการ DNS รองรับ) และต่ออายุอัตโนมัติ
4. เปิดพอร์ต 25 ขาเข้า, จำกัดอัตรารับต่อ IP, เปิดการตรวจ SPF/DKIM/DMARC ขาเข้า, ตัวกรองสแปม
   และ greylisting ของ Stalwart, การเรียนรู้สแปมจากการย้ายโฟลเดอร์ของผู้ใช้
5. ระบบรายงานชื่อเสียง: อ่านรายงาน DMARC ที่ส่งเข้ามา สรุปเป็นตารางในหน้าจอ และแจ้งเตือนเมื่อ
   IP ถูกขึ้นบัญชีดำ (ตรวจกับ Spamhaus/บัญชีดำสาธารณะเป็นรอบ)
6. โหมดลูกผสม: ตั้งค่าเส้นทางขาออกผ่านรีเลย์ภายนอกที่ระดับ Stalwart โดยรหัสผ่านอยู่ในคลังกุญแจ

เกณฑ์รับงาน
- คะแนนจาก mail-tester.com ไม่ต่ำกว่า 9/10 สำหรับจดหมายที่ส่งออกจากกล่อง
- Gmail และ Outlook รับจดหมายเข้ากล่องหลัก (ไม่ใช่สแปม) ใน 3 บัญชีทดสอบ
- ส่วนหัวจดหมายขาเข้าแสดงผล SPF/DKIM/DMARC ที่ตรวจแล้ว
- ใบรับรองต่ออายุเองได้ (ทดสอบด้วยการบังคับต่ออายุ)

ประมาณการ: 3 สัปดาห์ (ไม่รวมเวลารอผู้ให้บริการอินเทอร์เน็ตและ DNS)

### ระยะที่ 3 — ธรรมาภิบาลข้อมูล การปฏิบัติตามกฎหมาย และความทนทาน

เป้าหมาย: ให้โมดูลจดหมายผ่านเกณฑ์เดียวกับส่วนอื่นของ iVS ก่อนปล่อยในรุ่นที่แจกจริง

งาน
1. **ROPA**: แถวกิจกรรม "ระบบจดหมายอิเล็กทรอนิกส์องค์กร" ระบุประเภทข้อมูล (ที่อยู่จดหมาย, เนื้อหา,
   ไฟล์แนบ, ข้อมูลจราจร), ผู้รับข้อมูล (ผู้ให้บริการรีเลย์ภายนอก ถ้ามี) และระยะเวลาเก็บรักษา
2. **นโยบายเก็บรักษา**: ผูกกับ `retention_service` ที่มีอยู่ กล่องจดหมายของบัญชีที่ปิดถูกลบเมื่อครบกำหนด
   พร้อมบันทึกหลักฐาน SHA-256 เช่นเดียวกับการลบตาม GDPR
3. **สิทธิในการลบ**: ขยาย `gdpr_erasure_service` ให้รองรับเป้าหมายชนิด "mail" คือ ลบกล่องจดหมาย
   และบันทึกการส่งที่มีที่อยู่นั้น โดยเคารพข้อยกเว้นเรื่องข้อมูลจราจรที่กฎหมายกำหนดให้เก็บ
4. **ข้อมูลจราจรตาม พ.ร.บ.คอมพิวเตอร์**: เก็บบันทึกการรับส่ง (ผู้ส่ง ผู้รับ เวลา IP ผลลัพธ์ ไม่เก็บเนื้อหา)
   ไม่น้อยกว่า 90 วัน ประทับเวลาด้วย `ntp_service` และส่งออกได้แบบมีค่าแฮชเช่นเดียวกับ `AuditLogExport`
5. **สำรองและกู้คืน**: ขั้นตอนกู้คืนที่ทดสอบจริง (ไม่ใช่แค่สำรอง) และระบุไว้ใน OPERATIONS.md
   ว่าการ "ดีพลอยซ้ำ" ไม่กระทบ volume ของจดหมาย
6. **ความทนทาน**: กำหนด quota ต่อกล่อง (ค่าเริ่มต้น 2 GB) และเตือนเมื่อดิสก์เหลือน้อย
   ผ่าน `resource_service`; ตรวจสุขภาพ (health check) ของ `ivs-mail` แสดงใน `system-health`
7. **เอกสาร**: คู่มือผู้ใช้ภาษาไทย (ตั้งค่าโทรศัพท์, เว็บเมล), คู่มือผู้ดูแล (เพิ่มโดเมน, อ่านรายงาน DMARC),
   และปรับ `docs/IVS_Test_Plan.docx` ให้มีชุดทดสอบจดหมาย

เกณฑ์รับงาน
- ผ่านรายการตรวจใน `IVS_Verification_Checklist` ส่วนที่เพิ่มใหม่ครบทุกข้อ
- กู้คืนจากสำรองลงเครื่องเปล่าแล้วผู้ใช้เห็นจดหมายเดิมครบ
- คำขอลบข้อมูลที่อ้างที่อยู่จดหมายได้ผลภายในรอบเดียว พร้อมหลักฐานแฮช

ประมาณการ: 2 ถึง 3 สัปดาห์

## 7. ความปลอดภัย (ใช้ทุกระยะ)

- ไม่มีการรีเลย์แบบเปิดในทุกกรณี ทุกการส่งผ่าน 465/587 ต้องยืนยันตัว และพอร์ต 25 รับได้เฉพาะ
  จดหมายที่ปลายทางเป็นโดเมนของกล่องนี้
- บังคับ TLS: ปิดการยืนยันตัวแบบไม่เข้ารหัส, รองรับ TLS 1.2 ขึ้นไป
- รหัสผ่านทั้งหมด (ผู้ดูแล Stalwart, บัญชีต่อแอป, รีเลย์ภายนอก) อยู่ในคลังกุญแจเท่านั้น
  มีสิทธิ์ `allow_reveal=False` และหมุนได้จากหน้าจอ
- จำกัดอัตรา: ต่อบัญชี (เช่น 200 ฉบับ/ชั่วโมงสำหรับผู้ใช้, ตั้งแยกได้สำหรับแอป) และต่อ IP
  ที่ล็อกอินผิดซ้ำ (บล็อกชั่วคราวในตัว Stalwart)
- ไฟล์แนบ: จำกัดขนาด (ค่าเริ่มต้น 25 MB) และบล็อกชนิดไฟล์ปฏิบัติการ
- หน้าผู้ดูแลและ API ของ Stalwart ไม่เผยพอร์ตออกจากเครื่อง เข้าถึงผ่าน Caddy ที่มี app_gate กำกับ
- บันทึกตรวจสอบของ iVS บันทึก "ใครสร้าง/ปิดบัญชี, ใครเปลี่ยนโดเมน, ใครหมุน DKIM" ทุกครั้ง

## 9. การวางตำแหน่งผลิตภัณฑ์ รุ่นย่อย และใบอนุญาต

### 9.1 ผลิตภัณฑ์ 3 ระดับ (ตามข้อเสนอที่ยืนยัน)

| ผลิตภัณฑ์ | ลักษณะ | ตรงกับระยะในแผนนี้ | กลุ่มลูกค้า |
| --- | --- | --- | --- |
| **iVS Mail Free** | จดหมายสำหรับองค์กรขนาดเล็ก โดเมนเดียว บัญชีจำกัด (เสนอ 10 บัญชี) ภายในเครือข่ายหรือผ่านรีเลย์ภายนอก | ระยะที่ 0 และ 1 | SME ทดลองใช้, องค์กรที่ต้องการจดหมายภายใน |
| **iVS Mail Pro** | หลายโดเมน, บริหารผู้ใช้และโควตา, สำรองและกู้คืน, โดเมนจริงพร้อม DKIM/SPF/DMARC | ระยะที่ 1 ถึง 3 ครบ | SME และบริษัททั่วไป |
| **iVS Mail Enterprise** | หลายเครื่อง (multi-node), เฝ้าระวังรวมศูนย์, ความพร้อมใช้งานสูง (HA), บริหารจากศูนย์กลาง | ต่อยอดจากรุ่น Pro เมื่อ iVS Enterprise พร้อม | Enterprise และหน่วยงานภาครัฐ |

ระดับผลิตภัณฑ์เหล่านี้บังคับผ่าน `license_service` (แกน "ระดับ") ส่วนการมีหรือไม่มีเมนูบังคับผ่าน
`variants.py` (แกน "รุ่นย่อย") ตามหลักสองแกนที่ไฟล์นั้นอธิบายไว้ ไม่สร้างกลไกใบอนุญาตใหม่

### 9.2 การผูกกับรุ่นย่อยที่มีอยู่

| รุ่นย่อย | สถานะโมดูล `mail` | เหตุผล |
| --- | --- | --- |
| free | ระยะที่ 0 เท่านั้น (รีเลย์ภายนอก, ไม่มีเซิร์ฟเวอร์ในตัว) | ให้กล่องฟรีแจ้งเตือนได้ แต่เซิร์ฟเวอร์เต็มรูปเป็นคุณค่าที่คุ้มกับใบอนุญาต |
| hospital | เปิดครบ (เน้นระยะที่ 1 ในเครือข่ายปิด) | โรงพยาบาลมักอยู่ในเครือข่ายปิดและต้องการจดหมายภายใน |

## 11. การทดสอบ

- **หน่วย**: การจัดคิวและลองซ้ำของ mail_service, การเรนเดอร์เทมเพลตสองภาษา, การสร้างระเบียน DNS
- **บูรณาการ**: ใช้ `swaks` ทดสอบส่งผ่าน 587 แบบยืนยันตัว/ไม่ยืนยันตัว, ทดสอบรีเลย์เปิด,
  ทดสอบ IMAP ด้วย `imaptest` หรือไคลเอนต์จริง
- **ความน่าเชื่อถือขาออก** (ระยะ 2): mail-tester.com, ตรวจ `dig MX/TXT`, ส่งถึง Gmail/Outlook/iCloud
- **ความปลอดภัย**: สแกนพอร์ตจากนอกเครื่องต้องเห็นเฉพาะพอร์ตที่ตั้งใจเปิด, ทดสอบล็อกอินผิดซ้ำ
- **ปฏิบัติการ**: รีสตาร์ตกล่องแล้วคิวและกล่องจดหมายอยู่ครบ, กู้คืนจากสำรอง, ทดสอบธง `EVENT-LIVE`
- ชุดทดสอบทั้งหมดเพิ่มเข้า `docs/build_test_plan.js` เพื่อออกเป็นเอกสารแผนทดสอบฉบับเดียวกับระบบ

## 12. ข้อตัดสินใจ

### 12.1 ยืนยันแล้ว

| ประเด็น | ข้อสรุป |
| --- | --- |
| เครื่องยนต์จดหมาย | Stalwart Mail Server (ภาพคอนเทนเนอร์ทางการ ตรึงรุ่น) ไม่ Fork |
| ตัวเลือกสำรอง | Docker Mailserver สำหรับระบบที่ต้องการความเรียบง่าย |
| บทบาท | iVS เป็นชั้นบริหารจัดการและดีพลอย Stalwart เป็นเครื่องยนต์ ข้อมูลอยู่บนดิสก์/NAS ของกล่อง |
| รูปแบบการติดตั้ง | บริการระดับแพลตฟอร์ม `ivs-mail` ไม่ใช่แอปที่ดีพลอยซ้ำได้ (ดู 4.1) |
| เว็บเมล | แยกจากหน้าผู้ดูแล Stalwart เป็นคอนเทนเนอร์ `ivs-webmail` (Roundcube หากของ Stalwart ไม่พร้อม) |
| โครงผลิตภัณฑ์ | iVS Mail Free / Pro / Enterprise ตามหัวข้อ 9.1 |
| ไม่รองรับ | Mailcow เพราะทรัพยากรและข้อจำกัดบน Synology/QNAP ที่เอกสารทางการระบุ |

### 12.2 ข้อสมมติที่ใช้ดำเนินงาน (เปลี่ยนได้ด้วยการแจ้งครั้งเดียว)

คำถามสองข้อจากข้อเสนอเบื้องต้นยังไม่มีคำตอบชัดเจน แผนนี้จึงเดินด้วยข้อสมมติต่อไปนี้

1. **รูปแบบการให้บริการ: แบบลูกผสม (Hybrid)** กล่องทุกกล่องเริ่มจากจดหมายภายในองค์กรได้ทันที
   (ระยะที่ 1) และเปิดรับส่งกับอินเทอร์เน็ตเมื่อผ่านตัวตรวจเงื่อนไขของระยะที่ 2 แนวทางนี้ครอบคลุม
   ทั้ง Public และ Internal โดยไม่ต้องเลือกตั้งแต่วันแรก และตรงกับความจริงว่าหลายองค์กรไทยอยู่หลัง
   CGNAT หรือถูกปิดกั้นพอร์ต 25 ซึ่งทำให้แบบ Public ล้วนใช้ไม่ได้
2. **กลุ่มลูกค้า: ทั้งสองกลุ่ม** โดยใช้ลำดับ SME ก่อน (รุ่น Free และ Pro) แล้วจึง Enterprise และภาครัฐ
   (รุ่น Enterprise) เพราะรุ่น Enterprise ต้องรอความสามารถหลายเครื่องของ iVS Enterprise
3. บัญชีจดหมายผูกกับผู้ใช้ iVS หนึ่งต่อหนึ่ง และใช้รหัสผ่านแยกจากรหัส iVS
4. ระยะเวลาเก็บข้อมูลจราจร 90 วัน และกล่องจดหมายของบัญชีที่ปิด 1 ปี

### 12.3 ต้องตัดสินใจเมื่อถึงระยะที่ 2

- ผู้ให้บริการรีเลย์ภายนอกที่จะรองรับเป็นค่าตั้งต้นสำหรับโหมดลูกผสม (เสนอ Amazon SES และ SMTP2GO)
- โดเมนทดสอบที่จะใช้ยืนยันคะแนนความน่าเชื่อถือก่อนปล่อยรุ่น Pro
